## 0. 重写原则（比任何具体约束都重要）

**P1 · 纯服务端。**
本模块只 patch `Server.Game.*` / `HostPacketHandler` / `Managers` 等服务端类型。
**不 patch 任何客户端类型**（`RecordManager` / `UI_TrialEvent` / `PacketHandler` / 客户端 `Player` / `UI_GameScene`）。

为什么（这是现有实现最大的问题）：这些补丁**只在房主自己的进程里生效**（远程客户端没装插件）
⇒ 房主看到的画面 ≠ 别人看到的画面 ⇒ **测试结果被污染**（"改好了"只是房主这台改好了）；
更糟的是它**掩盖服务端方案的不完善** —— 正确的反应是"服务端换个不该出场的人"，
而不是"在房主本机把昵称关掉"。§10 列了现有实现的全部 8 处。

**P2 · 单一来源。**
每个决策只有一个地方做：窗口（`ReplayWindow`）、剪影（`SilhouetteResolver`）、出带（`TapeAssembler`）。
现有实现每样都有两到三份，这是所有"改 A 坏 B"的结构性来源。

**P3 · 传绝对时间区间，不传相对偏移。**
这是 P2 的具体形态，也是那个 6 秒偏移的直接成因：两条路各自解释同一组 `Before/After`，
而两条路的锚点不同（一个含 `atOffset`、一个不含）。区间一旦算出来就是**绝对时刻**，谁用都一样。

**P4 · 一幕一条结构化日志。**
现有实现一幕要打 5~10 条散落日志，出问题时要在几百行里拼。重写后每条幕只打一行，字段固定
（来源 / 窗口 / 帧数 / 主角 / 剪影 / 替身 / 备注），一眼能看出"这一幕发生了什么"。

**P5 · 合法性的判据是"对所有人是否生效"，不是"能不能做"。**

- **合法**：房主端造得出来、并经 `room.Broadcast` 送到**每一个客户端**的帧 ——
  **哪怕它是无中生有**（例如服务端伪造一段"出刀"动作）。
  因为所有人看到的是同一件事；这和"合成位置帧"没有本质区别 —— 回放本来就是重演。
- **不合法（这才是掩盖）**：只在**房主自己的进程**里生效的修改（客户端补丁）。
  它让房主看到的画面与别人不同 ⇒ 测出来的结论对别人不成立，
  而且会让"服务端方案到底行不行"这个判断失真。

⇒ 所以服务端合成的能力边界**不是**"不许编"，而是"**编出来的必须人人都能看到**"。
   服务端确实做不到的（例如客户端预制体里烘死的字幕），如实写进"已知限制"，不做局部掩盖。

**P6 · 配置键名可迁移。**
允许改段名（`EndReplay` → `Replay`），但必须走 `Core/ConfigMigration.cs`，
让用户 `.cfg` 里的定制自动搬到新键上（第 8 节列了 19 个必须保留语义的项）。

## 1. 客户端硬约束（违反 = 崩 / 卡死 / 整段静默跳过）

| # | 约束 | 证据 | 违反的后果 |
|---|---|---|---|
| C1 | 每段磁带 `Count >= 2` **且首帧是 `SpawnShot`** | `BeginTape :31905` | 静默跳过整段（连转场都不播） |
| C2 | `TimeStamp` 必须**非递减** | `Update :32010`：`if (TimeStamp > _currentTime) break;` | 大值夹在中间 ⇒ 那一帧 break ⇒ **后面所有帧不执行** |
| C3 | `PlayerId == _blackId` 的 `SpawnShot` **被无条件跳过**（不看时间戳、不做 ApplySpawn） | `Update :31997-32009` | 首帧锚点不会被"自己的"出场帧重新摆位（这是必要的，但必须知道） |
| C4 | `PlayerId == _myPlayerId` 的 `SpawnShot` 会被**改写成 0** | `Update :31999-32002` | 每台机器看到自己的替身；"幽灵替身恰好是某观众本人"⇒ 他那一份坏掉 |
| C5 | `ChangeMyPlayer(_blackId)` 是 `_cache[id]` **直接索引** | `:31926`、`:31525` | id 不在缓存里 ⇒ `KeyNotFoundException` ⇒ 整段回放中断 |
| C6 | `ChangeArea` 走 `RoomDic[RoomId]` | `:29607` | `RoomId = 0` ⇒ `KeyNotFoundException` |
| C7 | **每段必须自带 `NormalTimeEdit`** | `ApplyEdit :32167-32188` + `DeltaTime :28706` | 继承上一段遗留的 `TimeScale = 0.25` ⇒ 8 秒的带子要走 32 秒 ⇒ 只有开头几帧被执行（"哑剧"） |
| C8 | **不能发 `AddShot(Corpse)`** | `ApplyAdd` → `Corpse.SetInfo`；二次调用时骨架已被自己关掉 ⇒ `GetComponentInChildren<SkeletonAnimation>()` = null | NRE；而 `_playIndex++` 在 `switch` **之后** ⇒ 同一枚帧每帧重试 ⇒ **整段卡死** |
| C9 | **不能发指向"不在场景里的人"的 `EffectShot{FlashVfx/ScopeVfx/ArmbandVfx}`** | `PlayFlashEffect`/`PlayScopeEffect`/`PlayArmbandEffect` **都无条件解引用** `GetPlayerCache(effect.DeviceId)`（而它找不到只返回 null，这三个都不检查）| NRE；`_playIndex++` 在 switch **之后** ⇒ 同一帧每帧重试 ⇒ **整段卡死** |
| C10 | 剪影只打给 `_blackId` | `:31928-31931` `ChangeSilhouette(true)` | **首帧的 id 谁，谁被涂黑** |

> ★ **C9 反过来解释了「为什么要补全员出场帧」**：`EffectShot` 里的 id 必须在客户端的 `_cache` 里，
>   否则那三个特效函数解引用 null ⇒ NRE ⇒ 卡死。所以"让每个人至少有一枚出场帧"，
>   目的**不是**让画面好看，而是让**所有可能被 `EffectShot` 引用的 id 都已装配**。
>
> ⇒ 推论：**不要试图"不给幽灵补帧"来去掉他的昵称** —— 那会重新打开这个卡死口子。
>   昵称是观感问题、卡死是能不能玩的问题，不值得换。（2026-10 实测后回退过一次。）
> C8/C9 是"同一枚帧每帧重试"这个结构的后果 —— 只要有一枚帧会抛，**整段回放就永久卡住**。
> 所以宁可少一幕，也不要发不确定安全的帧。

## 2. 时间基准（最容易出错的地方）

- **T1** `shot.TimeStamp = isStartShot ? SurvivalTime : ClientTime`（`:31836`）
- **T2** ★ 每轮 `RecordAllType` 的**第 1 帧**（录制者自己）用 `SurvivalTime`，
  **同一轮的其余全员帧**用 `ClientTime`（`:31800-31810`，只有第一枚传 `isStartShot: true`）
  ⇒ 磁带的时间戳序列是 `[S, C, C, …, S, C, C, …]` —— **每 1 秒一个大跳**
- **T3** 实测：`S ≈ 463~502`、`C ≈ 65~114`，差 ≈ **388**（本局恒定，跨局会变）
- **T4** 服务端 `Managers.Game.ClientTime` 与客户端同源（都由 `S_TIME` 驱动）⇒ 房主侧可以拿它当基准
- **T5** ★★ **窗口必须只有一个定义。**
  现有实现有两条路各算一次：服务端合成用 `clip.At ± Before/After`，客户端磁带用 `磁带锚点 ± Before/After`。
  而 `At = ClientTime + atOffset` **含偏移**、磁带锚点（`NormalTimeEdit` = 事件时刻）**不含**
  ⇒ 两者差一个 `atOffset`。自爆幕 `atOffset = CollarToDeadSec = 6`
  ⇒ 客户端磁带路的窗口落在 `[t0−6, …]`（自爆**之前**），这就是"看不到闪烁"的结构性原因。

## 3. 录制端事实（决定了"素材里能有什么"）

- **R1** 只在 `IsAlive && !IsSpectator && State == Survive` 时录（`:31819-31822`）⇒ 死亡/旁观期**完全不录**
- **R2** 磁带**一定以录制者自己的 `SpawnShot` 开头**（`:31823-31834` 的空表守卫要求第一枚必须是自己的）
- **R3** 环形缓冲 `MAX_RECORD_LENGTH = 14`（`:31551`）⇒ 稳态只保留**最近约 14 秒**
- **R4** `RecordingTape[key]` 要到 `T + 9s` 才落地（`:31668`）；在此之前索取会走"当前缓冲"分支
- **R5** 移动帧密度 = `C_MOVE` 发包密度：`UpdateMovePacket` 跑在 `FixedUpdate`、节流 `>= 0.1f || 方向变更`（`:14865-14894`）
  ⇒ 站桩 ~10 Hz；转向**立即补发**；鼠标跟随时可达 FixedUpdate 频率（≈50 Hz）
- **R6** ★ **覆盖面 = AOI 内**：`Player.Move` 只 `Session.Send`(自己) + `BroadcastToDeadPlayers` + `BroadcastToPlayerAndObservers`（`:175910-175912`）
  而死者**不录制** ⇒ 活人交上来的磁带**只有 AOI 内的画面**（不是"全房所有人"）
- **R7** **未录制**：音效、物品增删、线索、任务进度、审判投票、绘图、尸体元数据、PrivateInfo、冷却、击退、表情
  ⇒ `PublicPlayerInfo` 的 8 个字段就是磁带里玩家信息的上限
- **R8** 假人**没有客户端** ⇒ 永远交不上磁带（只能服务端合成）
- **R9** 录制会产生的帧类型：`SpawnShot / MoveShot / AddShot / RemoveShot / DespawnShot / RespawnShot / ModifyShot / StateShot / AreaShot / EffectShot / DeadlyTrickShot / EditShot`

## 4. 素材来源（三条路的能力不同，不能当成同一件事）

| | 客户端磁带 | 服务端合成 | 占位磁带 |
|---|---|---|---|
| 谁能提供 | 真人（活过那一局） | 房主自己 | 房主自己 |
| **设备帧**（门/传送门） | **有** | 无 | 无 |
| 覆盖面 | AOI 内 | **全员**（采样） | — |
| 帧密度 | 10~50 Hz | 现在 5 Hz（**应改挂 `Player.Move` 以求同频**） | 2 帧 |
| 首帧 | 录制者本人 ⇒ 必须换 | 我们直接造 | 我们直接造 |
| 光照 | 每帧真实（`AreaShot.IsLight`） | 现在**硬编码**（**应改用采到的 `Row.IsLight`**） | — |

- **S1** **单 key** 请求 ⇒ 客户端 `trim = list.Count >= 2` 为 false ⇒ 回**原始缓冲**（我们自己裁）
- **S2** **多 key** 请求 ⇒ `trim = true` ⇒ 客户端按**硬编码** `killTime − 3f` ~ `_killLocalTime + 5f` 自己裁，
  且**分基**（下界用基 S、上界用基 C）
  ⇒ 我们自造的 key（`BaseKey + 100/200`）量纲不符 ⇒ **裁出空带** ⇒ 静默降级
  ⇒ **所以必须每个 key 单独发一包**
- **S3** `BuildUploadTape` 有四段 `return value` 回退（无 MyPlayer / 无基准时刻 / 无自身 SpawnShot / 结果 < 2 帧），
  每一段都会**放弃裁剪、返回原表**

### S4 · ★ 来源优先级（硬规则，不是优化）

```
客户端磁带  >  服务端合成  >  占位磁带
```

**为什么客户端磁带更好 —— 它录的是"玩家真正看到的画面"：**

| | 客户端磁带 | 服务端合成 | 差距性质 |
|---|---|---|---|
| 帧密度 | 事件驱动：站桩 ~10Hz、**转向立即补发**、鼠标跟随可达 ~50Hz | 现在死板 **5Hz** 定时采样 | **可消掉**（阶段 3 把采样改挂 `Player.Move`） |
| 位置 | 客户端本地位置（画面里就是它） | 服务端权威位置 = 收到 `C_MOVE` 后设的 `PublicInfo.Pos` | **消不掉**：恒定落后约一个 RTT（客户端是本地先行） |
| 设备帧 | **有**（门/传送门） | 无 | 结构性的 |
| 光照 | 每帧真实 | 现有实现硬编码 | 可修 |
| 覆盖面 | 只有 AOI 内 | **全员** | 服务端反而更好 |

⇒ **"延迟刀"的观感来源就是第二行**：服务端的位置落后于画面，凶手"走到位再出刀"在合成磁带里
   会显得迟滞。采样频率提上去能让它变顺，但**补不回那一跳**。

**因此：**
1. 能拿到客户端磁带时**绝不用服务端合成**（现有实现已是这个口径，保留）。
2. 服务端合成的定位是**最后手段**，不是"平行方案"。
3. **每一幕的日志必须标出来源**，让人一眼看出这一段是"真的"还是"编的"。
   ⇒ 用 <see cref="TapeOrigin"/> 表达，并写进那一幕的唯一日志行。
4. 已知限制如实记录：服务端合成**必然**有 RTT 级位置滞后、且不含客户端独有的设备帧。
   这不禁止我们去**改善**它 —— 例如补上攻击动作、把采样提同频。
   只要改动是**服务端产出并按 S4 分发给所有人**，它就是合法修复。
   被禁止的只有"只在房主本机生效"的修补（见 P5）。

## 5. 三个角色（必须分开命名 —— 这是最大的错误来源）

| 角色 | 含义 | 约束 |
|---|---|---|
| **SubjectId** | 镜头要拍谁 | 服务端合成时相机只能跟着他；**原版没有"把相机送到别的房间"的实现** |
| **RecorderId** | 谁能提供磁带 | 只有真人；假人为 0 ⇒ 必须服务端合成 |
| **SilhouetteId** | 首帧给谁（= 剪影落点） | **不能是 SubjectId**（否则他被涂黑）；**不能用 0**（服务端发的 id 0 会让每台机器都 `Spawn(0)` 建出多余玩家）。而**客户端自己**在"首帧 id == 它自己"时会折出 `_blackId = 0` —— 那无法避免，机制与代价见 §5.5 |

现有实现用一个 `Clip.RecorderId` 同时承担这三个含义，是反复出错的根源。

### 5.5 ⚠ `_blackId = 0`：已核实的机制 + ★ 仍在怀疑（**暂不修**）

**已核实**（`RecordManager.BeginTape` 的执行顺序）：

    ForceSpawnReplayTemp(MyPlayer.Name)   // ① 0 号替身 → _cache[0]（停在原点，从未被摆位）
    Despawn(所有人)                        // ②
    _blackId = (tape[0].Spawn.PlayerId != _myPlayerId) ? tape[0].Spawn.PlayerId : 0;   // ③
    ChangeMyPlayer(_blackId)              // ④ 镜头目标 → _cache[_blackId]
    ApplySpawn(tape[0].Spawn)             // ⑤ ★ 这一步才把 Players[0] 建出来
    if (Players.TryGetValue(_blackId, out var v)) v.ChangeSilhouette(true);   // ⑥ ⇒ **会执行**

⇒ `_blackId = 0` 时客户端里出现**两个不同的"0"**：

| 对象 | 是谁 | 被谁操作 |
|---|---|---|
| `_cache[0]` | `ForceSpawnReplayTemp` 造的**替身**，停在原点 | ④ 镜头跟它 |
| `Players[0]` | ⑤ **新建**的玩家（带首帧的位置与角色）| ⑥ 涂黑它 |

⇒ 正常情况（`_blackId = X ≠ 0`）两者是**同一个对象**，镜头与黑块是一体的；
  而 `= 0` 时它们**分家** ⇒ **镜头跟的是一个停在原点的替身**（这才是"0 不能当剪影位置"的真实代价）。

**我们的兜底**：`HostSynth.Frames` 把 `AreaShot` 放在**窗口起点**，它会把 `CameraTarget` 切到主角
⇒ **第 2 帧就纠正** ⇒ 实测代价只有 **1~2 帧的镜头错位**。
（旧实现没有这个保证，所以当时表现为**整段镜头不对** —— 那才是记忆里的"大问题"。）

#### ★ 仍在怀疑的部分（**暂不修，遇到了再说**）

1. **上面只是"镜头"这一条路径，别的后果没人清查过。**
   "两个 0 分家"意味着**任何依赖 `_cache[id] == Players[id]` 的客户端代码**，
   在那一台机器上都可能表现不同 —— 而我们**没有逐条排查**过此类依赖。
   ⇒ 所以这里标注为：**怀疑存在潜在 bug，未证实，未修。**

2. **可以彻底避免：按客户端分别发 `S_TAPE`。**
   服务端掌握 `PlayerId ↔ Session`（我一度说"不知道"，那是错的），而 `S_TAPE` 是普通下行包，
   定制成本也很低（只有首帧的 `PlayerId` 需要变）。
   **暂不做的理由**：
   - 需要**至少两个**"整段不可见"的候选，而实战的早期幕常常**只有 0~1 个**
     （没人死过 / 只有一名被处决者）⇒ 机制会**静默失效**，比现状更糟；
   - 它破坏「**一份数据、各自解释**」这条原则 —— `ApplySpawn` / `ApplyMove` / `ApplyState` 里那句
     `if (id == _myPlayerId) id = 0` 正是**故意让各台机器本地消化差异**。
     一旦开始按机器定制磁带，这个边界就破了，以后每个"某台机器不同"的问题都会被要求再分包。

#### 排障判据（"遇到了再说"的前提是能认出来）

- 日志里 `首帧(剪影)=#N` ⇒ **#N 那台客户端**走的就是这条路径；
  若他报告"回放开头镜头跳到奇怪的位置/原点"，先查**他那一台**的日志与画面。
- 若怀疑是上面第 1 条的未知后果，排查对象是：**依赖 `_cache[id] == Players[id]` 的调用点**
  （`ChangeMyPlayer`、`ChangeSilhouette`、`SetTargetEffect` 之类）。

## 6. 幕序与 key

- 客户端 `_playTapes` 是 `Dictionary<int, List<SnapShot>>`
  ⇒ **播放顺序 = key 顺序**，且**同 key 会覆盖**（后到者赢）
- 幕序（我们的口径）：**拿刀 → 杀人 → 最后时段 → 白方各段 / 自爆 → 黑方收尾**
- ⇒ key 必须**唯一且单调递增**。现有实现靠 `+1 / +100 / +200` 手工偏移 ⇒ 重写时应由**幕表下标**派生
- 反例（已踩）：`SurviveTime` 在结算时**已停走** ⇒ 所有请求拿到同一个 base ⇒ 必须自己加偏移区分

## 7. 结算编排

- 拦截点：`GameRoom.ChangeGameState(EGameState.TotalResult)` —— 三个调用点（`GameOver` 的推送 / `ClearAllMission` / `Trial.FinalizeTrialResult`）都走它
- 回放期间**服务端必须保持 `Survive`**：
  - `TrialTick`（`:171536`，`if (State == Trial)`）会跑 `Trial.Tick()` ⇒ **原版裁判状态机接管**并广播讨论/投票界面
  - `GameOver` 末尾是 `if (State == EGameState.Survive) PushAfter(7500, …TotalResult)`（`:171403`）
- 客户端进 `Trial` **只广播 `S_CHANGE_GAME_STATE`，不改服务端 State**
- 客户端的换状态是**异步**的（走加载过渡）⇒ 必须等回执（`WaitCompletePacket`）
- 必须发 `S_FADE_IN` 收掉加载页（否则要等 18 秒的 `CompleteWatchdog` 兜底）
- 推 `S_TRIAL_STATE{Replay}` **之前**必须把全部磁带发完 ——
  `StartReplay` 会把 `_playTapes` **快照**进 `_session`，之后再补就进不了这一轮
- `MasterMind` 是**跨局**的 `GameRoom` 字段 ⇒ 必须清，否则原版会向黑方弹「你的合作黑幕是 X」
- 白胜 / 黑胜的判定要显式记录（现有实现靠 `GameOverNoteHook` / `WhiteWinNoteHook` 两个"只做记录"的钩子）

## 9.5 ★ 并存期陷阱（实测踩过；阶段 6 之后结构上不再存在）

在"新旧两个实现同时在场"的期间，`HostPacketHandler.Handle_C_TAPE` 上会挂**两个 Prefix**：

- 新实现的 `TapeHook`：对**自己的 key** 返回 `false`（意图拦住原版的广播）；
- 旧实现的 `TapeHook`：对"不是自己的 key"返回 `true`（意图放行给原版）。

**实测结果：原版的 `Broadcast(S_TAPE)` 仍然执行了。**
索取回来的原始磁带被广播进所有客户端的 `_playTapes`（那就是回放的播放列表）
⇒ 回放多播了几段**未裁剪的完整 14 秒原始录像** ⇒ 播不完 ⇒ 卡在 Trial
⇒ 回大厅后客户端 UI 全部无响应（没有抛异常，所以日志里干干净净）。

⚠ **教训（写进原则）**：
   **"我拦住自己那一份"这种假设，在同一个方法上存在第二个 Prefix 时不能成立。**
   ⇒ 凡是靠"拦截别人"才能成立的功能，都不要与另一个实现并存；
   ⇒ 宁可等替换完成再启用，也不要为了"提前验证"而让两套逻辑同时在线。
   ⇒ 阶段 6 之后 `Handle_C_TAPE` 上只有一个补丁，这类问题结构上不会再出现。

> 附：`FetchRealTapes` 这个开关本身**不是**坏设计 —— 坏在设计它"依赖拦截"却允许并存。
>   正确的顺序是：**先替换、再验证**（那时 dump 由新实现自己落，出问题照样能离线分析）。

## 10. 现有实现里的客户端补丁（重写时**全部删除**）

现有 `EndReplayFeature.cs` 有 8 处 patch 客户端类型。逐个说明"它想解决什么"与"服务端视角下该怎么办"：

| 现有补丁 | 目标类型 | 想解决什么 | 重写时怎么办 |
|---|---|---|---|
| `ClientShowTrialUiHook` | `UI_GameScene.ShowTrialUI` | 诊断 + 清理字幕 | 删 |
| `ClearSlideText`（被上面调用） | — | 审判 UI 里那行**烘死的韩文**（`SlideText`） | 见 ※1 |
| `ReplayNameTagHook` | `UI_TrialEvent.StartReplay` | 黑方是本机玩家时，原版 `BeginSession` 关掉了**自己**的昵称 | **删**。`S_NOTIFY_BLACK` 本来就是服务端广播的 ⇒ 别人看得到；只有房主本机看不到，那是原版行为，不该偷偷改 |
| `ClientTrialStateHook` | `PacketHandler.Handle_S_TRIAL_STATE` | 诊断 | 删（诊断只覆盖房主本机 ⇒ 会误导） |
| `ClientPlayHook` | `RecordManager.Play` | 诊断 | 删 |
| `ClientBeginTapeHook` | `RecordManager.BeginTape` | 诊断 + 取 `_blackId` + 隐藏观察者昵称 | 删。`_blackId` 是**客户端内部状态**，房主侧本来就不该依赖它 |
| `AnchorNameTagHook` | 客户端 `Player.Refresh` | 观察者昵称每段会复活 | 见 ※2 |
| `HideAnchorNameTag`（上一条的辅助） | — | 同上 | 见 ※2 |

> 注意：`TapeHook`（`HostPacketHandler.Handle_C_TAPE`）**不是**客户端补丁 —— 它是服务端的，保留。

**※1 字幕（那行韩文）**
它是 `UI_TrialEvent` 预制体里烘死的，原版靠 `StartState(Discuss)` 的开场字幕序列收尾时
`slideText.SetActive(false)` 把它收掉。我们不走 `Discuss`（会触发客户端的"镜像状态驱动器"
进入**真的**讨论阶段，实测会冒出「开始讨论 / 投票」界面）。
⇒ **重写时按"不修"处理**，写进已知限制并在日志里注明。
⇒ 后续若要修，只走纯服务端路径调查：**有没有别的客户端 UI 可以当回放宿主**，从而根本不进 Trial。

**※2 观察者昵称**
本质是：**只要首帧那个人被 `ApplySpawn` 装配过，他就能出现在画面里**（`ChangeMyPlayer` 只是把镜头给他）。
服务端能做的是"挑一个观众不认识/不在场的人"（现有 `ResolveObserverId` 已在做），
但**无法让客户端不画他的昵称**。
⇒ **重写时按"不修"处理**，写进已知限制。
⇒ 后续若要修，优先调查**服务端可影响的显示项**：`PublicPlayerInfo` 的 8 个字段里有没有状态位能让
`Player.Refresh()` 不显示昵称（`EPlayerState.Hide` 是个候选）—— 而**不是**回到客户端补丁。


## 11. 回放模块必须存在的补丁目标（改动后逐条核对）

跑 `pwsh -File check-replay-equivalence.ps1 -Save` 之后，快照里 `## PATCH TARGETS` 段
必须**恰好**包含下面这些（多出来的要能解释清楚）：

| 补丁类 | 目标 | 作用 |
|---|---|---|
| `RoundStartHook` | `GameRoom.ChangeGameState(EGameState)` | 一局开始时清状态 |
| `SampleHook` | `Server.Game.Player.Move(PosInfo, bool)` | 主采样点（与客户端录制同频）|
| `HeartbeatHook` | `Managers.Update` | 1Hz 兜底采样（假人不发包）|
| `KnifeHook` | `Server.Game.Player.DelayAcquireWeapon` | 「拿刀」幕 |
| `HitHook` | `Server.Game.Player.OnDamaged` | 记"被击时刻"（`OnDead` 晚约 1.4 秒）|
| `KillHook` | `Server.Game.Player.OnDead` | 「杀人」幕 + 计数 |
| `CollarBombHook` | `Server.Game.Player.OnDeadCollarBomb` | 「自爆」幕 |
| `WhiteWinHook` | `WhiteWinFeature.TriggerWhiteWin` | 「巡礼」幕 |
| `BlackWinHook` | `GameRoom.GameOver` | 记录黑胜 |
| `SettleHook` | `GameRoom.ChangeGameState(EGameState)` | **拦结算**（Prefix）|
| `TapeHook` | `HostPacketHandler.Handle_C_TAPE` | **接客户端回包**（Prefix）|

### ⚠ 绝不能少的两个

- **`SettleHook`** —— 少了它，回放要么不触发，要么结算被原版抢先。
  它还有一个**致命细节**：`Finish()` 续结算时调的就是 `ChangeGameState(TotalResult)`，
  所以拦截判据**必须在 `Phase.Done` 放行**。实测踩过：判据写成"非 Idle 就拦" ⇒
  续结算被自己拦住 ⇒ **结算永远不会发生，游戏卡死**（日志里刷"继续拦截结算"）。
- **`TapeHook`** —— 少了它，客户端回的 `C_TAPE` 会落到原版 `Handle_C_TAPE`，
  而它直接 `Broadcast(S_TAPE)` ⇒ **未裁剪的原始磁带**进入所有客户端的 `_playTapes`
  ⇒ 幕序被打乱、回放被显著拉长。实测踩过：阶段 6 重写整个 `ReplayFeature.cs` 时漏了它。

> 教训：**重写整个文件时最容易漏东西**。改完就 `-Save` 一次再和上面这张表逐条对，
> 三十秒的事，比下一局打一半卡死便宜得多。

### ★ 三条"隐藏"通道互不覆盖（2026-10 逐行核实，替换掉早先模糊的说法）

客户端里有**三种独立**的隐藏，各自隐藏不同的东西，**互不覆盖**：

| 通道 | 谁控制 | 隐藏了什么 | 昵称 |
|---|---|---|---|
| `ChangeSilhouette(true)` | **客户端**（`BeginTape` 自动调，**只作用于 `_blackId` 一个人**）| 骨架涂黑 + `NameTag.SetActive(false)` | **关** ✓ |
| `PublicInfo.IsGhost` | **服务端**（逐帧字段）| 回放中：关 `_ghostRoot` 与 `SkeletonAnim` | **不管** ✗ |
| `PublicInfo.State = Hide` | 服务端（逐帧字段）| 只影响动画/逻辑 | **不管** ✗ |

⇒ **剪影的昵称本来就是关的**；能看到昵称的是**幽灵（`IsGhost = true`）**。

⚠ `IsGhostView()` **有两个实现**，这点必须记住，否则会得出相反结论：
- `MyPlayer`（子类，**本机玩家自己**）⇒ `!Managers.Game.IsAlive`（只看"我活着吗"）
- 基类 `Player`（**其他人**）⇒ `PublicInfo.IsGhost`
⇒ 所以 `IsGhost = true` 对**其他人**确实生效（回放中走 `case 2`：骨架与幽灵替身一起关）✓

### 磁带里的"死亡"是**时刻**，不是"幕的属性"

没有"本幕死者"这种标注。相关表达只有三种：

| 表达 | 粒度 | 含义 |
|---|---|---|
| `SpawnShot` / `DespawnShot` | **时刻事件** | 出场 / 消失（= 死亡那一刻）|
| `PublicInfo.IsGhost` | **逐帧** | 他此刻是不是幽灵 |
| `PublicInfo.State` | 逐帧 | 逻辑状态（`Idle`/`Run`/`Hide`…）|

⇒ 所以"让某人在整幕都不可见"不需要新标注，只要他**在这一段每一帧里 `IsGhost = true`**。

### 能标几个

- **剪影（涂黑）**：**只能 1 个** —— `_blackId` 由**首帧**唯一决定。
- **幽灵（`IsGhost`）**：**不限** —— 逐帧字段，而且可以"从某一刻起才变幽灵"。

### 昵称的已知限制（结论）

**服务端无解**：`NameTag` 不受任何磁带字段控制；能关它的只有客户端的
`ChangeSilhouette` / `SetForceHideNameTag`（旧实现曾用**只对房主生效**的补丁调它们 —— 那正是阶段 6 删掉的东西）。

⇒ 为什么"感觉昵称变多了"：`VisibleIn` 改成"从帧判断"之后被 spawn 的人**更全**（这是对的），
  而幽灵"身体看不见、名字还在" ⇒ 昵称跟着出现。**变的不是规则，是被 spawn 的人数。**
