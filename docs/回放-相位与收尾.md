# 回放：相位一致与收尾时机

> 这篇记的是**为什么**回放要那样写。两次"联机全炸"的排查都绕在这两条链上，
> 重新推导一次代价很大，所以把机制、证据与取舍固化下来。

---

## 一、ack 是什么

**ack = `C_COMPLETE_PACKET`** —— 客户端**主动上报**"我这一轮播完了"：

```csharp
// 客户端 RecordManager.Stop() 里
CompleteWatchdog.CompleteAndSend();
```

它不是超时。超时是 `WaitCompletePacket` 的另一个参数（绝对超时）。

### `WaitCompletePacket` 的三种结束方式（decomp:173015-173045）

```csharp
public void WaitCompletePacket(Action callback, int waitCount, int absoluteTimeoutMs, int firstAckGraceMs)
{
    ...
    if (waitCount == 0) CompleteAllPlayer();
    else PushAfter(Math.Max(1000, absoluteTimeoutMs), ForceComplete, callback);   // ③ 绝对超时
}

public virtual void CompletePacket(int playerId)
{
    if (_completeAction != null) {
        _completePlayerSet.Add(playerId);
        if (_completePlayerSet.Count == 1)                                   // ★ 第一个 ack
            PushAfter(_firstAckGraceMs, ForceComplete, _completeAction);      // ② grace 后收尾
        if (_completePlayerSet.Count >= _waitCount) CompleteAllPlayer();      // ① 全员到齐
    }
}
```

| | 条件 | 说明 |
|---|---|---|
| ① | 所有客户端 ack | `waitCount = CompleteWaitCount()` |
| ② | **第一个 ack + grace** | ★ 这条是"有人掉线时不死等"的兜底，**也是曾经的事故源** |
| ③ | 绝对超时 | `budget` |

**原版的语义是"等所有人看完"**，所以 ② 存在是合理的。但**回放不该用它**：那样"何时结束"就取决于"某台客户端什么时候发 ack"，而不是"内容播完了没有"。

## 二、相位分裂态：怎么形成的

### 我们的做法（刻意的）

```csharp
// ReplayDirector：只广播状态包给客户端，**不动服务端 State**
room.Broadcast(new S_CHANGE_GAME_STATE { State = EGameState.Trial });
// 并且回放期间把服务端按回 Survive（只写字段，不发包）
AccessTools.Field(typeof(GameRoom), "_state").SetValue(room, EGameState.Survive);
```

**为什么不动 `_state`**（`EnsureServerSurvive` 的注释，两条理由都成立）：

1. `GameRoom.TrialTick` 是 `if (State == Trial)` ⇒ 会每秒跑 `Trial.Tick()`，**原版裁判状态机接管并广播讨论/投票界面**，把回放覆盖掉；
2. `GameOver()` 末尾是 `if (State == Survive) PushAfter(7500, …TotalResult)` ⇒ 服务端不在 Survive，**结算那一步反而不执行**。

### 但分裂态有代价

guest 的**相位看门狗**读的是**快照里的 `Phase`**，而快照里的 `Phase` 就是**房主的 `GameRoom.State`**：

```csharp
// HostRuntime.BroadcastSnapshot（DummyClient:159748）
S_STATE_SNAPSHOT packet = new S_STATE_SNAPSHOT {
    Phase = (int)GameRoom.Instance.State,     // ← 分裂从这里进入 guest
    ...
};
```

```csharp
// 客户端 UpdatePhaseConvergence（decomp:34930-34943）
if (ShouldSkipPhaseConvergence(out var hostPhase)) { _phaseDesyncSeconds = 0f; return; }
_phaseDesyncSeconds += Time.deltaTime;
if (!(_phaseDesyncSeconds < 5f)) {
    Debug.LogWarning($"[Phase] 호스트 페이즈 불일치 {State} → {hostPhase} — 강제 수렴");
    Managers.UI.ApplyStateInstant(hostPhase);       // ← 被按回 Survive
}

// ShouldSkipPhaseConvergence（decomp:34955-34979）
if (Managers.Host == null || Managers.Host.IsHost) return true;   // ★ 房主永远跳过
...
hostPhase = SnapshotMirror.LatestPhase;
return hostPhase == Managers.Game.State;                          // 相等才跳过
```

⇒ 于是：**客户端 `Trial`、快照 `Survive`** ⇒ 满 5 秒 ⇒ 强制收敛。

### 而收敛会顺手发一个"与回放无关的 ack"

```csharp
// 客户端 ApplyStateInstant（decomp:38696-38715）
Managers.Game.State = state;
Managers.Game.CanControl = true;
sceneUI?.ResetFadeCover();
CompleteWatchdog.CompleteAndSend();        // ★★ 一个与回放无关的回执
```

⇒ **这个回执命中方式 ②**（第一个 ack + grace）⇒ 服务端以为"有人放完了" ⇒ grace 到点 `ForceComplete` ⇒ **全场回放被掐断**。

⇒ 实测吻合：真人局回放 ≈ **4 秒**（而 grace 是 4000ms），假人局 ≈ **18 秒**（假人没有客户端，这条链不存在）。

## 三、修法与判据

### ① 相位一致：改**快照**，不改 `_state`

⇒ `EnsureServerSurvive` 是**对的**，不能动。要改的是**看门狗读的那个字段**：

```csharp
// BroadcastHook 由 Postfix 改为 Prefix（否则包已发出去、改不动了）
if (packet is S_STATE_SNAPSHOT snap) {
    if (ReplayDirector.Current == ReplayDirector.Phase.Playing)
        snap.Phase = (int)EGameState.Trial;      // 让 guest 的比较成立
    return;
}
```

⇒ 效果：`hostPhase == Managers.Game.State` ⇒ `Trial == Trial` ⇒ **每帧跳过、计时器恒为 0** ⇒ 永不收敛。

**副作用面（已核实）**：全代码里读 `SnapshotMirror.LatestPhase` 的**只有两处** ——
`:34973` 相位看门狗（我们要影响的）与 `:173677` 主机迁移的**日志**。

### ② 收尾：由服务端预算单方面决定

```csharp
room.PushAfter(budget, () => Finish("预算到点"));      // 原来是 WaitCompletePacket(…, budget, 4000)
```

⇒ **不再看任何客户端的 ack**。代价是"播完的人可能多等几秒"，收益是"没有任何单台客户端能掐断全场"。

⇒ 另一处入场屏障同理：`WaitCompletePacket(WaitIntroThenReplay, …, 8000, 1500)` → `PushAfter(800, WaitIntroThenReplay)`。

⇒ `Finish` 是幂等的（`if (Current == Phase.Done) return;`），所以 `PushAfter` 与别处并发调用安全。

### 收尾保证

⇒ 服务端推 `TotalResult` 后，客户端 `EndReplay` 若发现还在播会**强制 `Stop()`**（decomp:71453）
⇒ **所有人一起收尾**，不会再出现"这台进结算了、那台还在播"。

## 五、边界：**不能完全避开 `Trial`**

⇒ 客户端只在 `ETrialState.Replay` 时才调 `StartReplay()`，而这个相位只能由 `S_TRIAL_STATE` 推
⇒ 推它就意味着客户端进 `Trial` 状态、创建 `TrialUI`（全代码里**只有 `ShowTrialUI`、没有 `CloseTrialUI`**，它靠场景销毁带走）。

⇒ 所以能做的是把这个借用**压缩成一个"有界、单进单出"的过程**：

```
进：推 Trial（客户端建 UI）→ 推 Replay（开始播）
出：预算到点 → 无条件推 TotalResult（客户端切出 Trial ⇒ 场景销毁带走 UI）
```

而不是"进去之后靠多方 ack 决定什么时候出来"。

## 六、没被证明的部分（诚实记录）

⇒ **guest 磁带的时间轴**：曾经假设"两台机器 `ClientTime` 不同 ⇒ 窗口错过帧 ⇒ 后两段坏"。
⇒ 但用现有 dump 量过：同一份磁带里 `SpawnShot`（整秒 `SurvivalTime`）与 `MoveShot`（本机 `ClientTime`）的差
**恒定 ≈ -388 秒**，且**跨录制者也几乎一致**（`#1` -388.1 / `#5` -388.04）。

⇒ **所以那个假设至少在这两台机器上不成立** —— "后两段坏"更可能属于：
"整场被掐断"（本文③已处理）/ 窗口真的无帧 / `C_TAPE` 包过大被丢（`SteamP2PSession.Send` 对 >512KB 直接丢弃，decomp:160628）。

⇒ 要区分它们，需要**那一次的服务端日志与 guest 的 `Player.log`**（`무효 shots=K` / `테이프 보관 t=N shots=K` 是关键行）。
