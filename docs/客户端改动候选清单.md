## 0. 为什么要有这份清单

1. 排查时很容易顺手提出"客户端补丁"（最直接、最省事），而它**与项目定位冲突**。
   与其每次重新争论一遍，不如把方案、代价、替代路线一次性记下来。
2. 保持纯房主端有一条**技术理由**，不只是偏好：**关键数据是服务端产出、再由服务端消费的**
   —— 比如回放首帧 id 是房主烘进磁带的，**没装模块的客户端拿到的还是同一个 id**，
   客户端护栏对他们**完全无效**。只有服务端侧修才对所有客户端成立。

### 现行事实：模块**已经**有客户端侧功能

| 事实 | 出处 |
|---|---|
| `ClientTapeProbe`（功能段 `[ReplayProbe]`，`side: Client`）会在客户端加载并回传磁带 —— 磁带回传本来就必须客户端配合 | 实机日志 `[HS] 已启用功能: ClientTapeProbe ([ReplayProbe], Client)` |

⇒ "客户端"这条线不是新问题；要守住的是**"修复的正确性不该落在客户端"**，
而不是"仓库里一行客户端代码都没有"（后者早已不是事实）。
⇒ 顺带：`PLAN.md` §0 那句"客户端不装任何东西"与该事实**不一致**，属于**待作者确认的定位表述**（不是本次要改的东西）。

## 1. 候选条目

### C-001 回放首帧 id 缺失护栏

| 项 | 内容 |
|---|---|
| **登记日期** | 2026-10-11 |
| **触发场景** | 回放首帧的剪影 id 在"磁带装配后、某一幕开始前"离开房间（退房/掉线/转 dummy）⇒ 客户端 `ChangeMyPlayer` 裸索引 `_cache[id]` 抛 `KeyNotFoundException` ⇒ `BeginTape` 死在 `[Replay] tape N/M 시작` 日志之前 ⇒ 整场回放一帧不播、客户端永久卡在录像画面、房主预算到点强推结算 ⇒ **房间必须重开** |
| **实证** | 2026-10-11 真人局；首帧剪影 `#7` 是中途加入的观战者，开播前 10 秒退房（原始材料在 `.tmps/回放故障-1011-末局一幕未播.md`，不进 git） |
| **改法** | Harmony **Prefix** 打在客户端 `RecordManager.BeginTape`：读 `_session[_tapeIndex][0].Spawn.PlayerId`；若它 `!= 本机 id` 且 `Managers.Player.GetPlayerCache(id) == null`，就把该磁带里引用这个 id 的帧（首帧 + `TapeAssembler` 注入的那枚 `RespawnShot`）改写成本机 id，并打一条中文 Warn |
| **为什么改写成本机 id 是对的** | 那样该机的 `_blackId` 会折成 `0`（`:32946`），走的是**文档已认可的退路**：0 号替身由 `ForceSpawnReplayTemp` 建好、`_cache[0]` 必然存在；`ApplySpawn` 也会把它改写成 0（`:33229-33232`）。代价＝不涂黑、镜头由 `AreaShot` 决定、仅残留一个角色名标签（`SilhouetteResolver.cs` 的类文档已写明这是"预期行为"） |
| **影响范围** | 只在"本来必卡死"的那台机器上，把该幕剪影退化成 0 号机位。正常路径零变化 |
| **风险** | **中** —— 改的是游戏核心回放方法；必须窄条件 + 全包 `try/catch`（护栏自身绝不能再变成第二个故障源），并只在捉迷藏回放期间生效 |
| **覆盖局限** | 只有**装了本模块**的机器受保护；未装的人仍会卡（这正是 §0 那条技术理由） |
| **为什么不现在做** | ① 违反 `PLAN.md` §0 定位；② 对未装模块的客户端无效；③ 服务端 S1-a/S1-c 已能消掉本次事故；④ 服务端 S2（按收件人定制首帧 id）提供一条**不碰客户端**的替代路线 |
| **替代路线** | 服务端 **S1-a**（候选池限定为本局参与者名单）+ **S1-c**（广播前复核，人不在就换占位带）已能消掉本次事故；**S2**（按收件人定制首帧 id）是唯一「不碰客户端也能把概率归零」的路，代价是剪影效果消失 + 磁带载荷 × 人数（`>512KB` 会被 `SteamP2PSession.Send` 丢弃）。**三者均未实施** |
| **状态** | **未实施**（仅登记） |

## 2. 维护规则

1. 新条目用 `C-00N` 顺序编号；**每条都必须写清"为什么不现在做"与"替代路线"**。
2. **不实施**的条目不许改代码、不许改配置默认值、不许因为"顺手"而落进提交。
3. 若某条最终被采纳：先在 `PLAN.md` §0 里改定位（或加豁免说明），再动代码，
   并回来把该条状态改成"已实施 `<提交>`"。
4. 被证伪/被替代的条目**不删除**，改成"已证伪（原因）"或"已被 `<条目>` 取代"。
